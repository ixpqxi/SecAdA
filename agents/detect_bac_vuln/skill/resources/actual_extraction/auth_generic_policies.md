# 通用授权模型代码实现提取指南

本指南不依赖特定的注解或内置函数，请完全基于控制流与数据流语义来逆向提取实际的鉴权实现逻辑。请严格遵循以下三个维度的特征追踪：

## 1. 身份上下文提取
在任何鉴权发生前，系统必须知道“当前是谁在操作”。请追踪目标 Controller / Handler 中的入口逻辑：
- **Token/Session 解析**：寻找类似于 `Session.get("user")`, `JWT.parse(token)`, `Request.getContext().getUser()` 的逻辑。
- **提取目标**：明确代码是否获取了当前用户的 `User ID` 或 `Role/Permission` 对象。若无此步骤，说明可能是未授权接口（严重警告）。

## 2. 基于数据流的鉴权提取
在一些系统中，鉴权不通过 `if` 语句，而是直接在数据库查询中进行过滤（即“查不到等于没权限”）。
- **追踪目标**：提取接口底层对应的 ORM 调用或原生 SQL 语句（如 `DB.query()`, `ExecuteSQL()`）。
- **核心提取规则（WHERE 子句分析）**：
  - 检查 SQL 拼接或 ORM 查询条件中，是否强制附带了类似于 `WHERE id = ? AND owner_id = ?`（当前登录用户 ID）的过滤条件。
  - 如果只有 `WHERE id = ?` 而未拼接当前用户信息，则存在严重的**水平越权（IDOR）**风险。

## 3. 基于控制流的鉴权提取
开发者可能会在业务逻辑执行前进行显式的条件拦截。
- **追踪目标**：寻找 Controller 开始处，或 Service 层核心逻辑执行前的条件分支（`if`, `switch`）。
- **核心提取规则（拦截逻辑分析）**：
  - **角色拦截**：寻找类似于 `if (user.role != 'ADMIN') { return 403; }` 的越权拦截语句。
  - **属主拦截**：寻找先执行 `SELECT` 获取资源实体，随后比对 `if (entity.creator_id != current_user.id) { throw AccessDenied; }` 的逻辑。
  - **提取要求**：必须明确指出代码是抛出了特定的异常（Exception）、返回了特定的状态码（401/403），还是直接终止了进程（exit/die）。

## 4. 防误报强制约束 (Anti-Hallucination Constraints)
- **拒绝伪造**：如果代码中没有明确看到上述的数据流（带 owner 的查询）或控制流（if 拦截），**绝对禁止**因为接口名是 `delete_order` 就假定它有权限校验。
- **证据要求**：在输出“实际鉴权实现”时，必须附带提取到的关键代码片段或伪代码结构作为凭证。
